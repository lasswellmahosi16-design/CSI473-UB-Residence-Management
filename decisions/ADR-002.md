# ADR-002 - Use ports and constructor injection for the verification workflow

- **Status:** Accepted
- **Date:** 2026-10-09
- **Context:** UB-DormHub Lab 9 detailed design
- **Related:** ADR-001, UC-04, QS-03, QS-04, Lab 8 API contract

## Context

The Verify Maintenance Report workflow must coordinate role checks, idempotency, current-state validation, a domain transition and multiple persistence writes. Directly calling framework/JPA classes from the controller or domain would make failure tests difficult and would reverse the dependency direction selected in ADR-001.

## Decision

1. Expose the operation through the inbound interface `VerifyMaintenanceReportUseCase`.
2. Implement the use case in `VerificationService`.
3. `VerificationService` receives all dependencies by constructor.
4. Persistence is accessed only through `ComplaintRepository`, `CertificationRepository` and `IdempotencyRepository` interfaces.
5. Role checks are accessed through `AccessControlPort`.
6. The complete state-changing operation runs through `TransactionRunner` so the implementation adapter can provide one transaction/Unit of Work.
7. `MaintenanceComplaint` remains the lifecycle owner; the service coordinates but does not duplicate the transition rules.
8. Framework/JPA/security classes implement the ports in outer adapters and depend inward on the core interfaces.

## Consequences

### Positive
- The core workflow can be unit-tested with fakes.
- Persistence failure and stale-state behaviour can be tested deterministically.
- Framework replacement is localised to adapters.
- Dependencies are visible in the constructor and class diagram.
- QS-04 has an explicit transaction boundary.

### Negative / accepted cost
- More interfaces and small adapter classes are required.
- Mapping between persistence entities and domain objects may be necessary.
- Developers must avoid creating interfaces with no boundary purpose.
- Transaction behaviour still requires integration tests against the selected database.

## Rejected alternative

**Controller -> concrete JPA repositories directly.** It is shorter initially, but it couples HTTP, workflow rules and persistence; makes transaction/failure behaviour harder to isolate; and encourages lifecycle rules to leak outside `MaintenanceComplaint`.

## Reconsider when

Revisit this decision if the verification workflow becomes trivial read-only logic, or if measured implementation complexity shows that a port adds no substitutable or testable boundary. Do not remove the transaction boundary while QS-04 requires atomic multi-record updates.
