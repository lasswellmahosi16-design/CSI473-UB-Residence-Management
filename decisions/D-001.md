# Architecture Decision Record: D-001 System Boundary & Verification Workflow Integration

* **Status:** Approved
* **Date:** 2026-08-10
* **Deciders:** Lasswell Mahosi, Jayson Maleya, Siphosethu Tsela, Thobo Modise, Tony Moroke
* **Traceability:** Addresses Student Welfare concern regarding paperless verification records and Maintenance Staff concern for clear work order queue dispatch.

## 1. Context & Problem Statement
Currently, UB uses a paper-based 3-copy verification form involving Student Welfare before a maintenance issue reaches the Maintenance Department. We need to decide whether the Student Welfare verification workflow belongs inside the core system boundary of UB-DormHub or if UB-DormHub should operate strictly as an internal ticketing system for the Estates/Maintenance Department.

## 2. Decision Considered
* **Option A (Chosen):** Include the Student Welfare Verification Engine inside the UB-DormHub system boundary as an explicit lifecycle state transition (`Reported` -> `Verified` -> `Assigned`).
* **Option B (Alternative):** Scope UB-DormHub to handle maintenance dispatch only, requiring Student Welfare to verify complaints outside the system via email/paper before manually injecting work orders.

## 3. Rationale & Choice
We chose **Option A** because paper-based or external email verifications are the primary cause of lost forms, duplicate requests, and lack of accountability. Bringing verification inside the system boundary ensures end-to-end traceability and gives students real-time visibility as their complaint moves through approval stages.

## 4. Consequences & Trade-offs Accepted
* **Positive Consequence:** Eliminates physical paper copies, reduces ticket loss to zero, and provides an unalterable audit trail for management.
* **Trade-off Accepted:** Increases the system complexity and user interface scope, requiring role-based access control (RBAC) screens for Student Welfare staff in addition to Maintenance and Student views.
