# D-002 — Domain Model Responsibility and Ticket-State Design

## Decision

Represent `MaintenanceTicket` as the central state-sensitive domain concept
and allocate ticket lifecycle behaviour to it, while assigning role-specific
responsibilities to Student Welfare, Maintenance Administration and Maintenance
Staff.

## Context

a non-trivial domain model is required with meaningful relationships,
business rules, responsibility allocation and traceability.

The UB-DormHub vertical slice is centred on:

**Report → Verify → Assign → In Progress → Resolved → Closed**

The model therefore needs a concept that can represent the maintenance problem
and its lifecycle without becoming a database schema or a collection of UI
screens.

## Options Considered

### Option A — Separate Report and Ticket Concepts

A `FaultReport` would represent the student's initial report and a separate
`MaintenanceTicket` would be created after verification.

**Advantages**
- Clearly separates initial reporting from maintenance work.
- Could support more complex future workflows.

**Disadvantages**
- Adds complexity to the initial vertical slice.
- Creates additional mapping between a report and its ticket.
- The current approved scope does not require two separate lifecycle objects.

### Option B — MaintenanceTicket as the Central Domain Concept

A `MaintenanceTicket` represents the reported maintenance problem and moves
through the defined lifecycle from `Reported` to `Closed`.

**Advantages**
- Directly represents the core project workflow.
- Makes ticket-status tracking explicit.
- Keeps the initial vertical slice smaller and easier to test.
- Allows business rules to be expressed around valid state transitions.

**Disadvantages**
- A future, more complex workflow may require separating a report from a
  work order.

## Decision Rationale

**Option B is selected** because it provides enough domain complexity for the
approved project while avoiding unnecessary modelling complexity.

The initial project requires reporting, verification, assignment, progress,
resolution and closure. A state-sensitive `MaintenanceTicket` represents
these concepts directly.

## Consequence

The initial implementation will use `MaintenanceTicket` as the central
workflow entity.

If future requirements introduce separate work orders, multiple maintenance
tasks per report or more complex escalation workflows, the model can be
refined later.

## Second Modelling Choice — Room and Residence

`Residence` contains one or more `Room` concepts, while a `MaintenanceTicket`
references the affected `Room`.

This was selected instead of attaching a ticket directly to a residence
because the maintenance problem occurs at a specific room level in the
approved vertical slice.

Composition between Residence and Room is justified for the analysis model
because rooms are being treated as parts of the residence structure within the
project domain.

## Consequence

The model can identify the exact room affected by a maintenance problem while
still grouping rooms under the selected residence.

## Deferred Features

Offline synchronisation, SMS, Microsoft Teams integration and immutable
logging remain outside this decision because the approval feedback explicitly says not to
include them.
