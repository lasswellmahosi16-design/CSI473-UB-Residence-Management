# D-003 - Preliminary Layered Component Boundary

**Status:** Proposed for Phase 1 architecture draft

## Context

UB-DormHub needs a small and maintainable architecture that supports the Phase 1 vertical slice of the residence maintenance process. The architecture should separate user interaction, application workflow, domain rules, and data persistence while allowing the system to be tested and changed without unnecessary technical coupling.

The architecture should support the main Phase 1 activities:

- Reporting maintenance faults
- Verification of reported faults
- Assignment of verified faults to maintenance staff
- Tracking ticket status
- Recording maintenance progress and resolution
- Closing completed tickets
- Role-based access to system functions

At this stage, the project should avoid committing to a specific web framework, programming language, or database technology.

## Options Considered

### A - Layered/Modular Web Application (Selected)

Use a single modular application divided into logical layers:

**Presentation → Application Services → Domain → Repository/Persistence**

### B - Microservices

Separate the system into independently deployed services for areas such as:

- Maintenance complaints/tickets
- Verification
- Work orders and assignment
- Reporting

## Decision

**Option A - Layered/Modular Web Application is selected for the Phase 1 architecture draft.**

The system will initially be developed as one application with clearly defined internal component boundaries.

The layers will have the following responsibilities:

- **Presentation:** Handles user interfaces, user input, navigation, and role-specific views.
- **Application Services:** Coordinates use cases such as reporting, verification, assignment, resolution, and closure.
- **Domain:** Contains UB-DormHub concepts and business rules, including ticket status transitions and validation rules.
- **Repository/Persistence:** Handles storing and retrieving system data while isolating the rest of the application from database-specific implementation details.

## Rationale

The Phase 1 vertical slice is relatively small and cohesive. A layered modular architecture provides sufficient separation without introducing the additional complexity of a distributed system.

Microservices would introduce additional concerns such as inter-service communication, deployment, distributed data consistency, service monitoring, and API management. There is currently no evidence that the Phase 1 system requires independent scaling or deployment of its individual functions.

The layered approach is therefore more appropriate for the current scope and team size while still allowing the architecture to evolve later.

## Architectural Principles

- Domain rules should remain independent of the presentation layer and database technology where practical.
- Application services should coordinate workflows rather than contain all domain business rules.
- Repository interfaces should isolate persistence technology from the domain and application layers.
- Role-based access control should be enforced at the application level and not only through the user interface.
- Components should have clear responsibilities and avoid unnecessary coupling.
- The architecture should remain simple enough to support the approved Phase 1 vertical slice.

## Consequences

### Positive

- Easier to implement and maintain than a microservice architecture.
- Clear separation of responsibilities.
- Easier unit and integration testing.
- Business rules can remain relatively framework-independent.
- Database or framework choices can be changed with less impact on the domain.
- Supports role-based access control and the required maintenance workflow.
- Provides a foundation for future expansion.

### Negative

- The system remains a single deployable application.
- Poor separation between modules could lead to tight coupling as the system grows.
- A future large-scale system may eventually require independently deployable services.

## Deferred Decisions

This decision does not yet determine:

- The programming language
- The web framework
- The database technology
- The hosting/deployment platform
- Authentication provider
- Whether any future module should become a separate service

These decisions can be made after the Phase 1 requirements and architecture have been validated.

## Future Reconsideration

The architecture can be revisited if UB-DormHub grows significantly or if there is a demonstrated need for independent deployment, scaling, ownership, or fault isolation of individual modules.

## Decision Summary

Use a **layered/modular architecture** for Phase 1 because it provides clear component boundaries, supports maintainability and testing, and avoids the unnecessary complexity of microservices.
